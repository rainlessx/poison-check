# poison-check

[English](README_EN.md) · **Русский**

Статический сканер безопасности для файлов ML-моделей: проверяет модель и её комплект, не загружая их.

---

## Проблема

Файл модели — это не только веса. Самый распространённый формат сериализации в экосистеме Python — pickle (и построенные на нём `.pt`/`.pth`, joblib, numpy object-массивы). Pickle при загрузке не «читается», а **исполняется**: поток опкодов может содержать вызовы `os.system`, `subprocess`, `eval`/`exec` и других примитивов, которые сработают в момент `torch.load` / `joblib.load` / `pickle.load` — до того, как вы хоть что-то сделаете с моделью. Это классический вектор RCE через цепочку поставки ML.

Но проверять только сам файл весов уже недостаточно. Современные модели поставляются **комплектом**: рядом с весами лежит код (`modeling_*.py`, `configuration_*.py`), а `config.json` через `auto_map` / `custom_pipeline` указывает, какой из этих файлов импортировать. При загрузке с `trust_remote_code=True` этот код исполняется как обычный Python — даже если сами веса лежат в безопасном формате `safetensors`. Опасность переезжает из файла в директорию, и файловый сканер её не видит.

poison-check исходит из обоих фактов: он разбирает структуру каждого файла модели **без его загрузки** (только чтение байтов, обход опкодов pickle, разбор заголовков), и отдельно проверяет **комплект** модели — исполняемый код рядом с весами и ссылки на него из `config.json`. Инструмент сообщает о найденных конструкциях как о фактах для ручного разбора, а не выносит вердикт «вредоносно» за человека.

## Возможности

Всё ниже соответствует фактическому составу сканеров и детекторов (`poison-check list-scanners`, `poison-check doctor`).

### Поддерживаемые форматы

| Сканер | Расширения | Что разбирает |
|---|---|---|
| `pickle` | `.pkl`, `.pickle`, `.dill`, `.pt` | Поток опкодов pickle (через `pickletools`, без исполнения) |
| `pytorch` | `.pt`, `.pth`, `.bin`, `.ckpt` | ZIP-контейнер PyTorch, вложенные pickle рекурсивно |
| `joblib` | `.joblib`, `.pkl` | joblib-стримы, в т.ч. сжатые zlib / lz4 / zstd |
| `numpy` | `.npy`, `.npz` | Magic bytes, object-dtype массивы, `.npy` внутри `.npz` |
| `safetensors` | `.safetensors` | JSON-заголовок и метаданные тензоров |
| `gguf` | `.gguf`, `.ggml` | Метаданные GGUF/GGML (llama.cpp, Ollama) |
| `keras` | `.keras`, `.h5`, `.hdf5` | Архитектура модели без загрузки keras/tensorflow |

Дополнительно проверяется **комплект модели** при сканировании директории: код рядом с весами и ссылки на него из `config.json` (`auto_map` / `custom_pipeline`).

### Что детектируется

Разбор фактов ведут 14 детекторов. Основные векторы:

- **Опасные глобалы pickle.** Модель `allowlist-first`: всё, что вне списка доверенных глобалов, помечается как подозрительное (`MLS-ALW-001/002`). Известные опасные глобалы и CVE — отдельно (`MLS-PKL-*`, `MLS-CVE-*`).
- **Примитивы выполнения кода в pickle.** `os.system` / `os.popen`, `subprocess.*`, `eval`, `exec` и др. (`MLS-PATTERN-*`). Известные CVE — по правилам из `rules/cve/` (например, CVE-2025-1550 — Lambda-RCE в Keras; CVE-2025-32434).
- **Исполняемый код в комплекте модели.** Файл `.py`, на который ссылается `config.json` (`trust_remote_code`), и опасные конструкции в нём с учётом позиции — module-level/загрузочная точка против обычного метода (`MLS-BUNDLE-001…004`).
- **Встроенные исполняемые файлы** внутри модели (`MLS-EXE-001`).
- **Подмена формата и code-bearing форматы** — например, pickle под видом safetensors (`MLS-FMT-001/002`).
- **Декомпрессионные бомбы** (`MLS-CMP-*`, `MLS-BOMB-001`).
- **Сетевые индикаторы** — URL и IP-адреса в содержимом (`MLS-NET-*`).
- **Секреты** — API-ключи, токены, пароли (`MLS-SEC-001`).
- **Метаданные форматов** — GGUF (`MLS-GGUF-*`), joblib (`MLS-JOBLIB-*`), numpy object-dtype (`MLS-NPY-001`).
- **Ошибки разбора** — непарсящийся или неполный файл не теряется, а помечается (`MLS-PARSE-001`).

### Отчёты

Форматы вывода (`--format`): `console` (по умолчанию), `json` (схема v1.0), `sarif` (SARIF 2.1.0), `sbom` (CycloneDX 1.4), `html`, `pdf` (требует extra `[pdf]`). Сообщения — на русском или английском (`--locale ru|en`). Инструмент работает офлайн: сети и телеметрии нет.

## Установка

Требуется Python 3.10+.

```bash
git clone https://github.com/rainlessx/poison-check.git
cd poison-check
pip install .
```

Обязательные зависимости (включая `lz4`, `zstandard`, `h5py`) ставятся автоматически — поддержка формата не зависит от того, что случайно оказалось в окружении.

Опциональные extras:

```bash
pip install ".[pdf]"   # PDF-отчёты (Jinja2 + WeasyPrint, тянет системные библиотеки)
pip install ".[7z]"    # распаковка 7z-контейнеров (py7zr)
```

Проверить окружение и состав правил/сканеров:

```bash
poison-check doctor
```

## Использование

### Команды

```bash
poison-check scan <путь>        # просканировать файл или директорию
poison-check list-scanners      # список поддерживаемых форматов
poison-check doctor             # диагностика окружения, правил, политик
```

### Основные флаги `scan`

| Флаг | Назначение |
|---|---|
| `--policy <имя\|путь>` | Политика: `default`, `banking`, `government`, `strict` или путь к своему YAML |
| `--format <console\|json\|sarif\|sbom\|html\|pdf>` | Формат отчёта |
| `--output <файл>` | Сохранить отчёт в файл (работает для всех форматов) |
| `-r`, `--recursive` | Обходить вложенные каталоги (по умолчанию выключено) |
| `--no-bundle-check` | Полностью отключить проверку комплекта модели (`MLS-BUNDLE-*`) |
| `--locale <ru\|en>` | Язык вывода |
| `--max-file-size <ГБ>` | Переопределить лимит размера файла |
| `--no-emoji` | ASCII-иконки `[!]/[*]/[i]` вместо эмодзи |
| `-v`, `--verbose` | Разбор глобалов по каждому файлу в stderr (диагностика ложных срабатываний) |
| `--client`, `--auditor` | Реквизиты для шапки отчёта |
| `--audit-log <файл>` | Дописывать строку JSON Lines на каждое сканирование |

Полный список — `poison-check scan --help`.

### Коды возврата

- `0` — находок уровня действия нет.
- `1` — есть хотя бы одна находка с severity `>=` порога `fail_on_severity` выбранной политики. Находки ниже порога попадают в отчёт, но гейт не валят.
- `2` — ошибка сканирования (файл не удалось разобрать и т.п.).

### Python API

```python
from poison_check import Scanner

result = Scanner(policy="default").scan("model.pt")

if result.has_critical:
    print(f"Критических находок: {result.summary.critical}")

for path, file_result in result.results_per_file.items():
    for issue in file_result.issues:
        print(f"[{issue.severity.value}] {path.name}: {issue.message}")
        if issue.decompiled_code:
            print(f"  Код: {issue.decompiled_code}")
```

`Scanner(policy=..., locale=...)`; методы `.scan(path, recursive=False)` и `.scan_bytes(data, filename=...)`.

## Уровни серьёзности

Уровень серьёзности определяется классом обнаруженной конструкции и её позицией:

| Уровень | Значение |
|---|---|
| `CRITICAL` | Обнаружена конструкция прямого исполнения кода в позиции, где она сработает при загрузке — максимальный потенциал RCE |
| `HIGH` | Обнаружена опасная конструкция с высоким потенциалом эксплуатации |
| `MEDIUM` | Подозрительная конструкция, требует ручной проверки |
| `LOW` | Низкий потенциал риска, информационно |
| `INFO` | Для полноты картины |

Severity отражает потенциальную опасность обнаруженной конструкции и её позицию, а не доказанную эксплуатируемость — итоговый вердикт за ревьюером.

Политики оперируют **двумя** независимыми порогами, и это важно понимать:

- `severity_threshold` — **порог внимания**: с какого уровня находка показывается крупно в отчёте (более низкие идут в раздел «ниже порога внимания», но не пропадают).
- `fail_on_severity` — **порог действия**: с какого уровня сканирование завершается кодом `1` (провал гейта CI).

Встроенные политики:

| Политика | `severity_threshold` | `fail_on_severity` | Назначение |
|---|---|---|---|
| `default` | medium | critical | Стандартный баланс полноты и шума |
| `banking` | low | high | Финансовые организации, повышенная строгость |
| `government` | low | high | Госсектор, акцент на соответствие ФСТЭК |
| `strict` | info | medium | Максимальная строгость для production CI/CD |

Свою политику можно задать YAML-файлом и передать через `--policy путь.yaml`.

## Границы и принципы

Эти границы — сознательный выбор, а не недоработка. Инструмент безопасности обязан быть точен в том, что он делает и чего не делает.

- **Только статический анализ. Код модели не исполняется.** Разбор идёт через `pickletools`-обход опкодов и разбор структур/AST. `pickle.load`, `torch.load`, `joblib.load`, `eval` на пользовательских данных не вызываются никогда.
- **Детектируется факт наличия опасной конструкции, а не доказывается вредоносность.** Это не SAST с анализом потоков данных: инструмент видит, что в загрузочном коде есть, например, `requests` или `exec`, но не доказывает, что вызов вредоносен. Легитимная модель может законно ходить в сеть при загрузке. Итоговый вердикт выносит человек при ревью — сообщения сформулированы как факты, а не приговор.
- **На неподдержанном или нечитаемом входе — fail-closed.** Файл, который не удалось разобрать (неизвестный формат, повреждение, неполная загрузка, недоступная зависимость), не проходит как «чистый»: он помечается отдельной находкой (`MLS-PARSE-001` и связанные). «Не проверено» никогда не выглядит как «безопасно».
- **Офлайн.** Сети, обращений к внешним сервисам и телеметрии нет.

Чего инструмент сознательно **не** делает:

- не исполняет и не «песочит» модель — никакого динамического анализа;
- не доказывает эксплуатируемость и не строит data-flow;
- не гарантирует обнаружение всех возможных угроз — это одно из средств проверки цепочки поставки, а не замена ручному ревью недоверенного кода;
- не «чинит» модели и не удаляет находки из файлов.

## Обратная связь

Pull request'ы **не принимаются** — проект развивается единым автором. Но **issues приветствуются**, особенно отчёты о срабатываниях на реальных моделях. Полезный отчёт содержит:

- модель (ссылка или описание) и формат файла;
- что сказал сканер (код находки, severity, сообщение);
- что вы ожидали (ложное срабатывание или, наоборот, пропуск).

Такие отчёты особенно полезны: они напрямую улучшают точность детекторов.
